# 并行实现手册（S2）

S2 能拆就拆：算出 ≥2 条互不冲突的车道就并行，只有拆不动（文件互相引用）才串行——
两个子代理改同一个文件，合并冲突比省下的时间多。

`split` 负责算这件事，这份手册说明它凭什么算、算完怎么派、派完怎么收。
**注意分工**：`split` 只产出方案与 prompt，真正「同时跑几个子代理」是主代理调宿主
子代理工具（本环境是 `Agent`）的动作，脚本不会自己开进程。

---

## 一、什么叫「互不冲突」

三条同时成立才算：

| 条件 | 判据 | 谁来核 |
|---|---|---|
| 文件不重叠 | 车道之间零文件交集 | `split --check` |
| 符号不互相引用 | A 的文件里没用到 B 定义的函数/类/常量（反之亦然） | `split --check` |
| 语义上互不相干 | 不同表迁移、不同接口、不同页面；不共用一个公共工具函数 | 人看一眼方案 |

第三条脚本判断不了，得你自己看。典型反例：

- 同一个 `UserService` 里改两个方法 → 同一文件，不能拆
- 两个迁移脚本改同一张表 → 不能并行
- 前端调后端新接口 → 后端接口没定，前端写不了 → 必须串行（或者先定契约再并行）

## 二、`split` 怎么算

```bash
python $DL split --root . --max 3 --check
```

1. **收集计划文件**：`state` 里未闭环项（`C1 | 文件 | 动作 | 理由`）→ `S1-影响面与方案.md` 的改造清单 → `影响面.json`，按优先级合并去重。
2. **算耦合**：对每对文件，看一方的文本里有没有用到另一方定义的符号（Python 走 AST，其余走正则）。用到的合并成一组——**它们必须由同一个子代理顺序改**。
3. **降噪**：同名文件（三个 `refund.*` 都会吐出 `refund`）不算证据；只在单个文件里定义、长度 ≥4 的符号才算。
4. **文档不参与符号耦合**：`.md` 引用了函数名不代表改代码会冲突，它由 S4 统一同步。
5. **按端配平**：先按文件类型（`.md` 文档 / `.sql` 迁移 / `.vue` 前端 / `.java` 后端），再看路径关键词，把组件分到最多 `--max` 条车道。

产物两份：`.devloop/S2-并行方案.md`（人看 + 派发模板）、`S2-并行方案.json`（含
`dispatch[]`，机器读）。`dispatch` 每条长这样：

```json
{
  "name": "lane-l1-后端",
  "files": ["src/api/refund.py", "src/service/order.py"],
  "prompt": "你只负责下面这些文件，不要碰其它文件：\n- src/api/refund.py\n…"
}
```

`parallel` 字段直接告诉你该不该并行（`lanes > 1`）。

`--check` 校验三件事：计划文件全覆盖、车道之间零文件交集、跨车道零符号引用。任何一条不成立就返回 3，**这时候不许并行**。

## 三、派发：一条车道一个子代理

**在一次回复里同时发起 N 个子代理**，不要发一个等一个——串着发等于串行，白拆：

```text
Agent(description="改 L1 后端", subagent_type="general-purpose",
      prompt=<dispatch[0].prompt>)
Agent(description="改 L2 前端", subagent_type="general-purpose",
      prompt=<dispatch[1].prompt>)
```

**每条车道都要交自检回执**：prompt 里已要求子代理把「改了哪些文件 / 命令 / 红 / 绿」
写进 `.devloop/回执/<车道名>.md`。这是脚本唯一能看到的"它到底验没验"的证据——
没回执、或回执里没有红/绿，`gate --stage S2` 直接拒收，主代理也补不出来（它没跑过那条车道）。

三个细节：

- `prompt` 用 `dispatch[i].prompt` 原文，**不要自己改写**——文件清单就是边界。
- 每个子代理的 prompt 里补一句需求背景与验收标准（从 `S0-需求澄清.md` 抄），
  否则它只知道改哪几个文件，不知道改成什么样。
- 不要给子代理开并行：它自己再拆一层，越界就查不清了。

再加三条硬约束（模板里已写，别删）：

1. **越界即作废**：子代理改到车道外的文件，这次结果不要了，重派。
2. **卡住先报告**：发现必须改车道外的东西，停下来回报，由主代理重算车道，不许自己动手。
3. **必须交证据**：改了哪些文件与关键行、跑了什么测试、**先红后绿的输出**（S2 的 TDD 证据就靠这个）。

## 四、收：主代理统一验

子代理交回来之后，**主代理**做这四件事，一件都不能少：

0. **先对账，再跑全量**：

   ```bash
   python $DL split --verify --cmd "python -m pytest -q"
   ```

   对账把实际改动按车道摊开：越界、漏改、整条车道没动，一次看全（`--allow` 放过
   `package-lock.json` 这类必然被改的文件；构建产物目录、S2 新增的测试文件都不算越界）。
   `--cmd` 接着跑一次**合并后的全量测试**——每条车道自己绿、合起来红，是并行最常见的事故，
   对账干净不等于能提交。两条都过才算收尾。
1. 跑**全量**测试（不是每个子代理自己那份）
2. 把各车道的红绿证据汇总进 `S2-实现.md` 的映射表——每条验收标准一行
3. 逐条回访用户「这条满足了吗」，原话记进「回访确认」
4. 进 S3 审计：`stage --stage S3` 会按 S1 清单对账，并行漏改的会在这里现形

## 四点半、跨端改动先定契约

前端 `.ts` 调后端 `.py` 的接口时，两边**没有任何可被脚本看见的符号引用**，
`split` 判"互不冲突"是对的，但接口其实耦合——实测里前端把 `amount` 改成必填、
后端加"金额必须大于 0"，各自都绿，合起来接口就断了。

所以只要本次改动**同时含前端与后端文件**，S1 必须写「接口契约」（`gate --stage S1`
会拒收没写的方案）：

| 接口 | 方法 | 参数 | 必填 | 返回 |
|---|---|---|---|---|
| /api/refund/{id} | POST | amount: number | 是 | {order_id, amount} |

写完这份表，两条车道照着它各改各的，才谈得上并行。

## 五、什么时候别并行

| 情形 | 为什么 |
|---|---|
| `split` 只算出 1 条车道 | 文件互相引用，拆开必然打架 |
| 改动集中在 1–2 个文件 | 拆了也是一个人干，白付上下文成本 |
| 有「先定契约」的前置 | 前端依赖后端接口，契约没定就并行 = 返工 |
| 同一张表的多个迁移 | 顺序错了数据就错，必须串行 |
| 正在排查一个说不清的 bug | 并行会同时引入多个变量，根因更难定位 |

## 六、和阶段门的关系

并行只改变「谁来写代码」，**不改变门禁**：

- 并行前：S1 方案和清单必须先确认（车道来自清单）
- 并行中：每条车道自己跑测试，但不单独登记门禁
- 并行后：S2 仍是一道门，审计的是**合并后的整体**，不是各车道各审一遍
