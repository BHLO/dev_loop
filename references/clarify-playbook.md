# 需求追问手册（S0）

S0 只干一件事：把「用户以为说清楚了」变成四条谈定的事。这份手册是问题的来源和话术模板，
SKILL.md §五 只写规则，具体问什么、怎么问、什么算问完，看这里。

---

## 一、四类问题：问到点子上

### 1. 目标范围

| 通用问法 | 后端（Java/Spring）追加 | 前端追加 |
|---|---|---|
| 谁在什么场景下遇到这个问题？现在怎么难受？ | 涉及哪些接口？有没有老版本客户端还在调？ | 涉及哪些页面/路由？有没有分享出去的深链？ |
| 这次要做的边界到哪？明确不做什么？ | 只改服务端，还是也要动网关/定时任务/消息消费？ | 只改展示，还是也要改交互流程？ |
| 有几个入口会走到这段逻辑？ | Controller、MQ Listener、Job、RPC 各有没有入口？ | 有没有从别的页面跳进来、或者被嵌入 iframe？ |
| 谁是这次的需求方？验收由谁拍板？ | 有没有下游系统依赖这个返回值结构？ | 有没有埋点/统计口径要跟着改？ |

**问不出后果**：方案做偏，改了一堆没人用的地方，真正的入口反而没覆盖。

### 2. 边界异常

| 通用问法 | 后端追加 | 前端追加 |
|---|---|---|
| 空值、0、超大值、超长字符串分别怎么处理？ | 金额用分还是元？精度到几位？负数要不要拒？ | 输入超长时截断还是报错？ |
| 重复提交、重复消费怎么处理？要不要幂等？ | 幂等键是什么（业务单号 / 请求号 / 唯一索引）？ | 连点两次按钮怎么办？ |
| 失败、超时、重试的策略？ | 调外部接口超时几秒？重试几次？失败要不要补偿？ | 请求失败时是弹提示还是静默重试？ |
| 并发场景下数据会不会串？ | 事务边界在哪一层？要不要SELECT FOR UPDATE 或乐观锁？ | 同一份数据在两个 tab 改，以谁为准？ |
| 存量数据不满足新规则怎么办？ | 老数据要不要刷？刷的时候停服吗？ | 老缓存/本地存储要不要清？ |

**问不出后果**：上线后第一笔脏数据、第一次重复点击就出事。

### 3. 验收标准

要求：**每条都能被一个测试验证**，带数值或可观察结果。

- 差的写法：「退款要正确」「性能要好」「体验流畅」。
- 好的写法：「退 30% 时，退款金额等于订单金额 × 30%，精确到分」
  「同一退款单号提交两次，退款记录只有一条，第二次返回第一笔的结果」
  「万级 SKU 下列表接口 P95 < 300ms」。

必问：

1. 怎么判断做完了？能不能逐条列出来？
2. 谁来验、在哪个环境验（本地/测试/预发）、用什么数据验（真实脱敏/构造）？
3. 有没有「差不多就行」的部分？哪些可以后续迭代？

**问不出后果**：「做完了」无法判定，验收靠感觉，最后一轮轮返工。

### 4. 约束兼容

| 通用问法 | 具体到 |
|---|---|
| 存量数据和老接口要兼容吗？兼容多久？ | 版本兼容窗口、灰度策略 |
| 能不能加表、加字段、改字段类型、改接口签名？ | DBA 审批、迁移脚本、回滚方案（**命中敏感文件，见 §12**） |
| 性能、权限、审计日志有硬要求吗？ | QPS/延迟目标、数据权限范围、是否要留操作日志 |
| 能引入新依赖吗？ | 中间件版本、内网能否拉包、包体积 |
| 出问题怎么回滚？ | 开关、双写、数据回补 |

**问不出后果**：动手时才发现表不能改、接口不能动、依赖引不进来。

## 二、弹窗怎么问：一轮一类，3–4 个

一次问太多，用户会挑着答，剩下的就悄悄丢了。推荐节奏：

```
第 1 轮  目标范围 3 问      → 落表 → 复述确认
第 2 轮  边界异常 3–4 问    → 落表
第 3 轮  验收标准 2–3 问    → 落表（这一轮必须问出可测的句子）
第 4 轮  约束兼容 3 问      → 落表
```

弹窗里**给选项**，别给空白输入框：

> Q：重复提交怎么处理？
> A1 幂等，同一单号只产生一笔（推荐）
> A2 允许重复，每次都是一笔新的
> A3 拒绝第二次，返回错误
> A4 其他：____

选项本身就是一次设计评审——用户看到 A1/A2/A3，往往会说「等等，A2 有问题」，
这比你问「要不要幂等」有效得多。

**每轮结束复述一句**：「我理解的是：…… 对吗？」
用户答「对」才算这一类收敛，答「不完全」就再问一轮。

## 三、答案含糊怎么办：追问阶梯

| 用户说 | 不要这样 | 这样追 |
|---|---|---|
| 「差不多就行」 | 直接按自己的理解写进方案 | 「差不多是指误差 1 分以内可以，还是必须一分不差？」 |
| 「看情况」 | 方案里写「视情况处理」 | 「两种情况各是什么？我列出来你选。」 |
| 「你定」 | 自己定完就往下走 | 「我建议 A，因为……；B 的代价是……。选 A 可以吗？」（要一句「可以」） |
| 「跟以前一样」 | 假设自己知道「以前」 | 「以前是指 XX 那个实现吗？我念一遍你确认。」 |
| 「先这样，后面再说」 | 当成已确认 | 记进「待定与假设」，标 `ASSUMED`，S1 方案里作为「待确认项」再问一次 |

**原则**：可以假设，但假设必须写在纸上、标出来源、再被确认一次。悄悄假设是返工的源头。

## 四、收敛自检（填完 S0 报告，逐条打勾）

- [ ] 需求原话是**原样引用**，不是我改写后的版本
- [ ] 问答表 ≥ 4 行，四类各至少一条
- [ ] 每一行的「用户答案」列都是用户说的，不是「待定」「待填」
- [ ] 验收标准 ≥ 1 条，每条都能被一个测试验证（带数值或可观察结果）
- [ ] 待定项都有处置办法（问、假设+确认、或明确不做）
- [ ] 我复述过一遍理解，用户答过「对」

`check --stage S0` 会替你核前四条；后两条靠自觉，但用户会看出来。

## 五、实现完的回访（S2 收尾）

**逐条念，不要笼统问「这样可以吗」。** 笼统问只会得到笼统的「嗯」。

模板：

> 需求里的这几条我实现完了，你逐条看下：
>
> 1. 退 30% 时金额 = 订单金额 × 30%（测试 `test_partial_refund` 先红后绿，实际退 30.00）——这条满足了吗？
> 2. 同一退款单号重复提交只有一笔（`test_idempotent`，第二次返回第一笔结果）——满足了吗？
> 3. 手续费按比例分摊（这条在 S0 里是 `ASSUMED`，我按比例做的）——这样算对吗？
>
> 有哪条不对我打回重做；都行的话我把「回访确认」写进报告。

用户答复原样记进 `S2-实现.md` 的「回访确认」，包括打回的那几条。
**打回的必须回 S2 重做**，不许先标完成再补——否则「验收标准」就只是文档里的装饰。

## 六、什么时候可以跳过 S0

只有三种情形，且都要显式 `--skip --note`：

1. **纯报错修复**：现象、期望都明确（「这个 500 要消掉」），走 S6。
2. **纯代码体检**：不改行为，只出问题清单，走 S5。
3. **纯文档同步**：代码没动，只补文档，走 S4。

新需求、需求变更、「帮我看看这个需求」——一律走 S0。
拿不准要不要走，就走——多问四个问题，比返工一次便宜。
