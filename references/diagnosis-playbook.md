# 诊断手册：健康检查 + 缺陷定位

---

## 第一部分：健康检查五维细则

### 1. 正确性

| 检查点 | 怎么看出来 |
|---|---|
| 边界值 | 循环 `0`、`1`、`len-1`；分页 offset 越界；日期跨月跨年 |
| 空值 | 返回值可能为 null 却直接 `.foo`；集合为空却取 `[0]`；可选参数未判空 |
| 异常路径 | try 范围过大吞掉异常；catch 后不处理只用 `print`；finally 里 return |
| 事务边界 | 事务里做 RPC/发消息/写文件；嵌套事务；异常没回滚 |
| 并发 | 共享可变状态无锁；先查后改（check-then-act）；单例里的成员变量 |
| 幂等 | 重试会重复插入/重复扣减；缺少唯一键或状态机保护 |
| 数值 | 金额用 float；整数溢出；精度丢失（除不尽） |

### 2. 安全

| 检查点 | 怎么看出来 |
|---|---|
| 注入 | SQL 字符串拼接；`exec`/`eval`；命令拼接；模板注入 |
| 越权 | 只校验登录不校验归属（`findById(id)` 没有 `and user_id=?`） |
| 敏感信息 | 日志打印手机号/身份证/token；异常信息直接返回前端 |
| 密钥 | 硬编码在源码/配置文件并提交到仓库 |
| 反序列化 | 不可信数据直接反序列化为对象 |
| 上传/下载 | 未校验类型与大小；路径穿越 `../` |
| 依赖 | 已知高危版本（提示用户跑 `npm audit` / `pip-audit`，不要自行断言 CVE） |

### 3. 性能

| 检查点 | 怎么看出来 |
|---|---|
| N+1 | 循环里查库/调接口；ORM 懒加载在序列化时触发 |
| 无界查询 | `select *` 无 limit；全表扫描；列表接口不分页 |
| 缺索引 | where 条件字段无索引；隐式类型转换导致索引失效；前模糊 `like '%x'` |
| 重复计算 | 循环里重复构建相同对象；循环里读同一配置 |
| 资源 | 流/连接未关闭；线程池/连接池无上限；缓存无过期 |
| 大对象 | 一次性把大文件/大列表读进内存 |

### 4. 可维护性

- 函数超过 80 行 / 嵌套超过 4 层 / 圈复杂度 > 10
- 同一段逻辑复制到三个以上地方（该抽未抽）
- 魔法值：状态码、类型值直接写字面量，没有常量或枚举
- 命名误导：`getXxx` 实际会写库；`isValid` 返回的是字符串
- 死代码：注释掉的整段代码、永远为 false 的分支、未使用的 import
- 注释与实现不符（比没有注释更危险）
- 空 catch / 空 if 分支

### 5. 架构

- 分层越界：controller 直接拼 SQL；service 里处理 HTTP 参数
- 循环依赖：A 引 B、B 引 A（编译能过但设计有问题）
- 公共层被业务污染：工具类里出现具体业务字段
- 隐式耦合：靠全局状态/静态变量传值
- 环境硬编码：IP、域名、路径写死

**分级标准**
- **P0**：会导致线上故障、数据错误、安全漏洞。必须修。
- **P1**：特定条件触发的问题、明显性能隐患、错误处理缺失。排期修。
- **P2**：可读性、风格、重复代码。随手修，不单独提。

**只报能落地的**：每条必须能回答「改哪一行、改成什么」。

## 第二部分：缺陷定位七步法

### 第 1 步 现象结构化

收集齐再动手，缺什么就明确问什么：

```
报错原文：
完整堆栈：
触发操作：
发生时间 / 频率：
环境（本地/测试/预发/生产）：
最近变更（git log / 发布记录）：
影响范围（单个用户 / 全部 / 某个租户）：
```

### 第 2 步 栈帧映射

- 从上往下取**第一个属于本项目的帧**（跳过 `spring`、`node_modules`、`site-packages`、`java.base`）
- 读该帧前后 30 行，注意：入参来源、空值判断、分支条件、外部调用
- 注意行号与代码可能不同步（热更新、编译产物、sourcemap 缺失）——行号对不上时以方法名为准

### 第 3 步 无堆栈时的定位手段

| 手段 | 适用 | 命令 |
|---|---|---|
| 日志回溯 | 有日志系统 | 按 traceId / 用户 id / 时间窗捞 |
| 二分注释 | 逻辑分支多 | 注释掉一半路径，看现象是否消失 |
| 开关隔离 | 有 feature flag | 关掉最近上线的开关 |
| 提交二分 | 怀疑某次发布 | `git bisect start; git bisect bad; git bisect good <sha>` |
| 字符串考古 | 想找某段逻辑何时引入 | `git log -S "关键词" --oneline -p` |
| 复现脚本 | 本地能跑 | 写最小脚本，逐步逼近 |
| 类型/静态检查 | 疑似类型问题 | `mypy` / `tsc --noEmit` / `go vet` |

### 第 4 步 根因分类

| 类别 | 特征 | 修复方向 |
|---|---|---|
| 数据 | 只有特定记录出错，换个用户就好了 | 清脏数据 + 加输入校验 + 加兜底 |
| 逻辑 | 稳定复现，条件写错/边界算错 | 改条件 + 补边界单测 |
| 并发 | 偶发、压测才现、日志时序错乱 | 加锁/改队列/改幂等键/乐观锁重试 |
| 环境 | 本地好、线上坏；换机器就好 | 对齐版本与配置；补部署清单 |
| 依赖 | 最近升级了包/三方接口变了 | 锁版本 / 适配新协议 / 加降级 |
| 容量 | 数据量涨上来才出现 | 加索引 / 分页 / 缓存 / 异步化 |

**分类错了修复一定错**：并发问题当逻辑问题改，会变成"改了还在偶发"。

### 第 5 步 证据链

没有证据链的判断只能标"疑似"。可接受的证据：

- 一个能稳定复现的失败单测
- 一段日志，能显示关键变量在出错时的实际值
- 二分结果：注释掉 A 段后现象消失，加回来又出现
- `git bisect` 定位到具体提交

### 第 6 步 最小修复

- 改一处，不要顺手重构。重构和修复分成两个提交。
- 优先选**可回滚**的方案：加开关 > 改逻辑 > 改数据结构。
- 同时给出**临时缓解**（止血）和**根本修复**（治本），让用户决定先做哪个。
- 明确影响半径：这次改动会影响哪些调用方 —— 直接触发 S2 重新审计。

### 第 7 步 验证

1. 跑相关单测（没有就现写一个覆盖该缺陷的）
2. 按原始复现步骤重跑
3. 验证相邻路径没被带坏（同一函数的其他分支）
4. 回到 S2：`python $DL impact --base HEAD~1` 确认修复本身的影响面
5. 把「复现用例」沉淀成回归测试，写进 S2 的待补测试清单

## 第三部分：常见缺陷模式速查

| 现象 | 高概率根因 |
|---|---|
| 偶发 500，日志指向空指针 | 并发下共享状态被覆盖；缓存击穿返回 null |
| 本地正常线上 500 | 配置缺失 / 环境变量没注入 / 版本不一致 |
| 数据只增不减、内存持续上涨 | 缓存无上限 / 监听器未解绑 / 集合只 add 不 remove |
| 接口慢但 CPU 不高 | 等 IO：N+1 查询、串行调用、锁等待 |
| 定时任务重复执行 | 多实例无分布式锁 / 任务超时被重复调度 |
| 金额算错几分钱 | float 精度 / 四舍五入时机 / 分与元单位混用 |
| 中文变乱码 | 编码链路不一致（DB/连接/文件/响应头） |
| 改了没生效 | 缓存 / CDN / 构建产物 / 部署了旧包 / 配置中心没推 |
| 只在特定用户出现 | 数据问题 / 权限过滤条件 / 灰度分组 |
| 上线后缓慢劣化 | 连接池泄漏 / 日志文件涨满磁盘 / 索引失效 |
