# 影响面核查规则库

脚本只能找到符号引用（谁 import 了、谁调用了）。语义影响必须按下面六个维度人工核查。**每一条都要给出 `文件:行` 依据，或明确写"无影响（原因）"。**

---

## 维度 1：接口契约

| 检查项 | 判定问题 | 典型位置 |
|---|---|---|
| 函数签名 | 增删参数、参数顺序、默认值变化 | 被调用方、SDK 封装、mock |
| 返回值结构 | 字段增删改、类型变化、null 语义 | 调用方解构、前端取值 |
| 错误码 / 异常 | 新增异常类型、错误码含义变更 | 全局异常处理、前端提示文案 |
| 接口路径与协议 | path / method / 入参位置（body↔query）变化 | 网关路由、前端请求封装、第三方对接 |
| 版本兼容 | 是否需要新老版本并存 | 客户端强制升级策略 |

**判定原则**：签名或返回结构变化 → 所有调用点默认「需要检查」，只有逐一确认过才能标「不需要改」。

## 维度 2：数据与 schema

- 表结构：加字段（是否有默认值/是否 NOT NULL）、改类型、加索引、加唯一约束
- 迁移脚本：是否需要 up/down、是否可重复执行、大表变更是否锁表
- 数据兼容：老数据能否被新代码读出；新数据能否被老代码读出（灰度期间双向）
- 缓存：key 结构变化是否要清缓存、TTL 是否合理、缓存与 DB 的一致性
- 搜索/索引：ES mapping、全文索引是否需要重建
- 导出/报表：字段增删会影响下游对账、BI、数据仓库

## 维度 3：配置与开关

- 新增配置项 → 各环境配置文件、配置中心、部署清单（k8s ConfigMap / docker env）是否都加
- 默认值 → 未配置时的行为是否安全（尤其开关默认值，默认开启等于全量放开）
- 灰度开关 → 关闭时是否回退到旧逻辑，回退路径是否被测过
- 环境差异：本地能跑、测试能跑、生产缺配置是高频事故

## 维度 4：上下游与异步链路

- 上游：谁调用我（HTTP/RPC/MQ 消费方），能否容忍新行为
- 下游：我调用谁（三方 API、其他服务），配额、超时、重试、幂等是否变化
- 消息：topic / tag / 消息体结构 / 消费组订阅关系变化
- 定时任务：执行时间、分片、并发度、幂等、失败补偿
- 长事务与补偿：是否需要分布式事务、对账补偿任务

## 维度 5：权限与安全

- 新接口是否接入了鉴权（不要只靠前端隐藏）
- 数据权限：能否越权查到别人的数据（水平越权）；角色权限矩阵（垂直越权）
- 敏感字段：是否新增了需要脱敏/加密的字段，日志是否会打印
- 审计：关键操作是否要留痕

## 维度 6：前端与文案

- 页面/组件：字段变更导致渲染报错、空态、超长文本截断
- 表单校验：前后端校验规则要一致
- 文案与国际化：多语言 key 是否补齐
- 交互：错误提示是否还能被用户看懂（后端错误码变了前端没跟）

## 各技术栈专项

**Java / Spring**
- `@Transactional` 边界：同类内部调用不生效；事务里发 MQ 会丢消息
- Bean 循环依赖、`@Autowired` 注入点
- MyBatis Mapper XML 与接口不同步（改字段只改了 Java）
- DTO/VO/Entity 三处转换遗漏（最常见漏改点）

**Python / Django / FastAPI**
- serializer / pydantic model 与 ORM model 不同步
- migrations 未生成（改了 model 忘了 makemigrations）
- 异步函数里混用同步阻塞调用
- 全局中间件对新增路由的影响

**Node / TypeScript**
- 类型定义与实际返回不一致（any 掩盖）
- `package.json` 依赖版本变化影响构建产物
- SSR 环境下 window/document 访问
- 环境变量在构建期注入 vs 运行期注入

**Go**
- 指针/值接收者方法集差异
- context 传递与超时
- 结构体 tag 与 JSON 字段名（改字段名会破坏兼容）
- goroutine 泄漏

**前端（Vue/React）**
- props 类型与默认值变化
- store / 全局状态结构变化
- 路由守卫与权限
- 组件库升级带来的样式或 API 变更

## 回归范围推导规则

对每个受影响对象打分，决定测多深：

| 条件 | 结论 |
|---|---|
| 接口契约变化 / 数据写入逻辑变化 / 权限逻辑变化 | **必测**：正向 + 边界 + 异常 + 权限越权 |
| 只改内部实现，输入输出不变 | **必测**：原有单测 + 冒烟 |
| 纯配置/文案/样式 | **抽测**：主流程一遍 |
| 新增分支但默认不触发（开关关闭） | **必测**：开关开/关两条路径 |
| 改动在死代码 / 未被引用 | **免测**，但要在报告里注明是死代码 |

**必测的三个通用场景**（任何改动都要覆盖）：
1. 老数据在新代码下的读取
2. 新数据在老代码下的读取（灰度回滚）
3. 失败路径：下游超时、空返回、异常抛出

---

## 常见漏改点（按命中率排序）

1. 改了 DTO / model，没改对应的转换层和序列化注解
2. 改了接口字段，没改前端取值和 mock 数据
3. 加了配置项，没加各环境配置文件和部署清单
4. 改了枚举值，没改前端下拉选项和数据库存量数据
5. 改了字段类型，没做数据迁移脚本
6. 加了权限点，没在后端真正校验（只在前端隐藏）
7. 改了消息结构，消费方没同步升级
8. 改了公共方法，只改了当前调用方，其他调用方没验证
9. 删了字段，还留着旧数据引用和报表 SQL
10. 改了错误码，前端提示文案和监控告警规则没跟
